# 基于 RAG 的校园领域智能问答系统

> 面向校内规章制度的本地检索增强问答系统。**核心目标不是"答得多"，而是"答不出来时明确拒答，绝不编造"。**

一套完全离线运行的 RAG 问答系统：把校内分散的制度文档（培养方案、学籍管理、考试规定、评奖办法等）整理成可检索的知识库，用户用自然语言提问，系统基于检索到的原文作答并给出可回溯的出处。

最大的挑战不是检索，而是**抑制大模型的幻觉**。实测直接向模型提问，会得到语言通顺但数字编造的答案（编造率 **75%**）。本项目的重点就是把它压到 **5%**，并让"答不出来"变成明确的拒答而不是硬答。

---

## 核心结果

| 指标 | 裸模型 | 朴素 RAG | **本系统** |
|---|---|---|---|
| 答案编造率（人工盲评） | 75% | 0% | **5%** |
| 应拒答问题正确拒答率 | 0% | 0%（从不拒答） | **100%** |
| 检索 Recall@5 | 0.000 | 0.807 | **0.912** |
| 检索 MRR | — | 0.559 | **0.649** |
| 端到端耗时 | — | — | **2.6–6.8 s**（拒答路径 0.006 s） |

> 评测集：自建 **85 题**（事实型 47 / 流程型 28 / 跨文档 5 / 应拒答 5），每题标注标准答案、答案所在文本块、是否可回答。划分 dev 61 题（调参）/ test 24 题（冻结）。
> 完整方法与数据见 [`eval/`](eval/) 下的实验记录。

## 系统架构

```
【离线】文档 → 知识库
  PDF/Word/TXT/HTML
      │  解析（含表格单元格合并）
      ▼
  文本清洗（全角半角归一 / 去页眉页脚 / 修复折行断字）
      │
      ▼
  语义切分（按标题层级递归切 → 相邻小块自底向上合并）
      │  286 块，每块 400–600 字
      ▼
  BGE-small-zh 向量化（512 维，L2 归一化）
      │
      ▼
  FAISS IndexFlatIP  ★ 元数据登记（文档族/版本/生效日期/状态）

【在线】提问 → 回答
  用户提问
      │
      ▼
  BGE 编码（查询侧加指令前缀）
      │
      ▼
  FAISS 检索 Top-5
      │
      ├─ 最高分 < 0.45 ──────────────► 拒答（不调用生成模型）
      │
      ├─ 最高分 ≥ 0.62 ──────────────┐  （早停：跳过 LLM 判定）
      │                              │
      └─ 否则 ──► LLM 逐块判定 ──────┤  （最多 3 块，任一可答即放行）
                     │               │
                     └─ 全部不可答 ──► 拒答
                                     │
                                     ▼
                          组装上下文 → 生成答案 + 引用编号
                                     │
                                     ▼
                          ★ 生成侧守卫：若模型自己输出拒答话术
                            则按拒答处理并清空引用
```

## 三个关键设计

### 1. 三层拒答防线

| 层 | 机制 | 作用 |
|---|---|---|
| **检索层** | 相似度阈值 0.45 初筛 | 挡住"明显不相关"，成本最低（毫秒级） |
| **判定层** | LLM **逐块**判断"这段资料能否回答本问题" | 挡住"看起来相关但答不了" |
| **生成层** | 捕获模型自发的拒答话术 | 兜住前两层漏掉的 |

**为什么逐块判定而不是拼接判定**：把所有块拼成一段再问一次，实测准确率 79%；改为逐块提问后提升到 **93%**。多个块混在一起时，模型容易被无关内容干扰。

### 2. 生成侧守卫（一个后期才发现的缺陷）

即使判定层放行，生成模型仍可能自己输出"知识库中未找到相关依据"。此时接口返回 `refused=false`（看似正常回答），但内容是拒答话术，且 `sources` 里还挂着无关引用 —— **用户无法分辨"没找到"和"这就是答案"**。

修复方式：检测"以拒答话术开头且剩余内容只含引导语"的答案，按拒答处理并清空引用。用"以…开头"而非"包含"来判断，避免正常回答中引用该话术时误判。

### 3. 主动放弃 rerank —— 一个否定结果的实验

引入 Cross-Encoder 重排后：

| | 无重排 | 有重排 |
|---|---|---|
| Recall@1 | 0.446 | **0.623** ↑ |
| MRR | 0.649 | **0.779** ↑ |
| 拒答查准率 | **0.211** | 0.182 ↓ |
| 可答侧放行率 | **0.737** | 0.684 ↓ |

**检索指标明显变好，端到端反而变差。** 根因是分数口径不一致：重排分数存进 `rerank_score`，而下游两道阈值读的还是稠密相似度 `score`；重排把更相关的块提上来时，其稠密分数往往更低，于是"越重排越容易在阈值处被拒"。

修复量纲问题后过拒仍未改善 —— 说明本场景**瓶颈根本不在检索**，加重排是引入无效复杂度。**结论：不启用。**

> 附带的教训：引入新信号时，必须审计所有消费旧信号的判据。这类 bug 不报错、测试能过，症状和原因在代码里离得很远。

## 快速开始

### 环境要求

- Python **3.11**
- [Ollama](https://ollama.com/)（本地部署大模型）
- Node.js 18+（仅前端需要）
- 内存 8 GB+；有 8 GB 显存的 GPU 更佳（纯 CPU 也能跑，只是慢）

### 1. 安装依赖

```bash
pip install -r requirements.txt
```

### 2. 拉取模型

```bash
# 生成与判定共用的本地模型（约 3B，4-bit 量化后约 2 GB）
ollama pull qwen2.5:3b
```

嵌入模型（`BAAI/bge-small-zh-v1.5`）由 `sentence-transformers` 首次运行时自动下载；如需完全离线，可提前放到本地目录并在 `config.py` 里指定路径。

### 3. 准备语料

把自己的文档放进 `data/raw/`（支持 `.pdf` / `.docx` / `.txt` / `.html`），然后在 `data/meta/documents.csv` 里登记元数据（`doc_id`、标题、文档族、版本、生效日期、状态等）。

字段说明见 `scripts/03_register.py` 表头的校验规则。

### 4. 构建知识库

```bash
python scripts/01_parse.py        # 解析为纯文本
python scripts/02_clean.py        # 清洗归一
python scripts/03_register.py     # 登记元数据
python scripts/04_chunk.py        # 语义切分
python scripts/05_build_index.py  # 向量化 + 建索引
```

### 5. 启动服务

```bash
# 后端（需先启动 ollama serve）
python -m uvicorn backend.main:app --port 8000

# 前端
cd frontend && npm install && npm run dev     # http://localhost:5173
```

### 6. 命令行试问

```bash
python scripts/06_ask.py "考试不及格可以补考吗？"
```

## 已知局限

**这个系统有一个明确的短板，我选择如实记录而不是掩盖。**

**过度拒答**：dev 集 57 道可答题中约 20 道被误判为"不可回答"（≈35%）。

例如问"补考一般安排在什么时候"，资料里写了"理论课程安排在下一学期第一、二周"，系统仍然拒答。

用四组实验定位过，全部无效：

| 尝试 | 结果 |
|---|---|
| 扩大判定窗口（3 块 → 8 块，覆盖全部 gold 块） | 过拒数**一项都没减少** |
| 引入 Cross-Encoder 重排 | 检索指标提升，端到端**反而变差** |
| 改写判定 Prompt | 离线台架上看有效，**干净环境交错 A/B 后逐题结果完全相同** |
| 调整相似度阈值 | 安全窗口仅 0.0019 宽，调整即过拟合 |

**结论**：瓶颈在本地 3B 模型的判定能力，不在检索、不在排序、也不在 Prompt。换更大的模型可缓解，但会违背"完全本地离线部署"的设计前提。

目前 35% 的过度拒答是一个**主动取舍**：在校园规章场景下，"说不知道"远比"编一个"危害小。

其他局限：

- 无真实用户，评测集为自建，缺少真实场景反馈
- 文档版本冲突处理的支持不完整（机制已实现，缺少真实多版本文档验证）
- 未做并发压测；问答接口尚未限流
- 不支持多轮对话与指代消解（`prompts.py` 中已预留改写 Prompt，尚未接入）

## 一个方法论收获

做这个项目最意外的一件事：**评估环境本身会成为实验变量。**

一次 Prompt 优化的台架测试显示"过度拒答 16 → 9"，看起来是成功的改进。但当时后端服务正在运行，评估脚本与后端**同时向同一个本地 Ollama 发请求**，GPU 争用改变了输出分布。停止服务后做交错 A/B 对照（旧→新→旧→新）：两种 Prompt 的过拒数**都是 20**，逐题判定**完全相同**。

更危险的是：被污染的测量**看起来是可复现的**（连测两次都是同一个值），极易被当成真实结果接受。

所以本地 LLM 的评测必须做到：
1. 单进程、无服务占用；
2. **交错对照**（A→B→A→B），而不是"先测完 A 再测 B"；
3. 保留一个**本应无差异的对照组**来探测环境噪声；
4. "连测两次一致"不等于结论可靠。

详见 [`docs/失败案例集.md`](docs/失败案例集.md) 中的相关条目。

## 技术栈

| 层 | 选型 |
|---|---|
| 语言 | Python 3.11 |
| 大模型 | Qwen2.5-3B（4-bit 量化，Ollama 本地部署） |
| 嵌入模型 | BGE-small-zh-v1.5（512 维） |
| 向量检索 | FAISS `IndexFlatIP`（精确内积） |
| 后端 | FastAPI + SSE 流式输出 |
| 前端 | Vue 3 + Vite + Element Plus |
| 数据库 | SQLite（WAL 模式） |
| 文档解析 | pdfplumber / python-docx / BeautifulSoup |

**没有使用 LangChain 等框架** —— 为了精确控制流程的每一步以便做消融实验，也为了出问题能直接定位到具体环节。
