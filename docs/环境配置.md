# 环境配置与常见问题

本文记录本项目的完整运行环境，以及搭建过程中实际踩到的坑。
**这些不是从文档抄的，是实际遇到并解决过的**，按"现象 → 原因 → 做法"记录。

## 一、硬件与系统

| 项 | 本项目实际配置 | 说明 |
|---|---|---|
| CPU | Intel i5-12450H | CPU 推理也能跑，只是慢 |
| GPU | NVIDIA RTX 4060 Laptop（8 GB 显存） | 3B 模型 Q4 量化约占 3.3 GB |
| 内存 | 16 GB | 建议 16 GB 起；8 GB 会很紧 |
| 系统 | Windows 11 | Linux 同样可行（路径配置需调整） |

**显存估算**（3B 模型）：

| 环节 | 占用 |
|---|---|
| Qwen2.5-3B Q4 量化 | ≈ 3.3 GB |
| BGE-small-zh 嵌入模型 | ≈ 0.3 GB |
| Cross-Encoder 重排（若启用） | ≈ 0.5 GB |
| **合计** | **≈ 4.1 GB**，8 GB 显存有余量 |

> 若同时运行后端服务与评估脚本，**两者会争抢同一块 GPU** —— 这是实测发现的问题，
> 会导致评估结果不可复现。跑评估前务必停掉后端服务。

## 四、实际踩到的问题

### 问题 1：`ollama` 模型下载速度只有 90 KB/s

**现象**：`ollama pull` 卡在几十 KB/s，几小时下不完。

**原因**：直连官方源在国内很慢。

**做法**：用国内镜像或代理下载 GGUF 后手动导入：

```bash
# 方式一：ModelScope 下载 GGUF 文件，再用 Modelfile 导入
ollama create qwen2.5-3b-q4 -f Modelfile

# Modelfile 内容示例
# FROM ./qwen2.5-3b-instruct-q4_k_m.gguf
# PARAMETER num_ctx 4096
```

> 注意：**分片的 GGUF（多个 part 文件）无法直接导入 Ollama**，
> 需要先合并成单文件。

### 问题 2：`pip install` 卡住或报源不可用

**现象**：默认 PyPI 源超时；换成清华源后返回空包列表。

**做法**：改用阿里云源。

```bash
pip install -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple/
```

### 问题 3：嵌入模型下载失败（`HF_HUB_OFFLINE`）

**现象**：启动时报无法连接 huggingface.co。

**做法**：先联网下载一次模型到本地缓存，之后设置离线模式：

```bash
set HF_HUB_OFFLINE=1
set TRANSFORMERS_OFFLINE=1
```

或在 `config.py` 中指定本地模型路径，彻底避免联网。

### 问题 4：端口被占用 / `address already in use`

**现象**：重启后端时报端口 8000 被占用，但看起来进程已经关了。

**原因**：Windows 下 `python -m uvicorn` 会留下**子进程**，父进程退出后子进程仍在监听。
更隐蔽的后果是：**新代码没生效，老服务还在跑** —— 会得到前后矛盾的测试结果
（本项目实际因此误判过一次）。

**做法**：按端口查 PID，用 `/T` 结束整棵进程树：

```cmd
netstat -ano | findstr :8000 | findstr LISTENING
taskkill /F /T /PID <PID>
```

`/T` 是关键参数，不加它杀不干净。

### 问题 5：SQLite 数据库文件被其他进程锁定

**现象**：`PermissionError` 或 `database is locked`。

**原因**：资源管理器预览、杀毒软件扫描会持有文件句柄。

**做法**：
- 启用 WAL 模式并设置 `busy_timeout`（代码已内置）
- 把数据库放到独立目录（本项目为 `data/db/`），避免被目录级操作影响
- 极端情况下重启资源管理器进程释放句柄

### 问题 6：WAL 模式的附带文件被提交进 Git

**现象**：`git status` 里出现 `app.db-shm`、`app.db-wal`。

**原因**：`.gitignore` 只写了主库文件名，没写 WAL 衍生文件。

**做法**：

```
*.db
*.db-wal
*.db-shm
```

### 问题 7：中文日志乱码 / 写入报编码错误

**做法**：显式设置输出编码。

```powershell
$env:PYTHONIOENCODING='utf-8'      # PowerShell
set PYTHONIOENCODING=utf-8         # cmd
```

### 问题 8：`.bat` 脚本中文全乱、报"不是内部或外部命令"

**现象**：脚本里写的中文和 `──` 制表符被当成命令执行，直接报错退出。

**原因**：`cmd.exe` 按系统 ANSI 代码页（简体中文为 GBK）读取 `.bat`，
而文件是 UTF-8 保存的，中文和框线字符被解析成乱码指令。

**做法**：**`.bat` 文件内容全部使用纯 ASCII**（不写中文、不写制表符），
或用 PowerShell 脚本（`.ps1`）。

### 问题 9：`timeout /t` 在重定向环境下报错

**现象**：脚本里用 `timeout /t 2 /nobreak >nul` 等待，输出
`ERROR: Input redirection is not supported`。

**原因**：`timeout` 需要控制台输入句柄，stdin 被重定向时不可用。

**做法**：改用 `ping` 做延时：

```cmd
ping -n 3 127.0.0.1 >nul
```

### 问题 10：FastAPI 依赖注入静默失败

**现象**：接口报错信息与真实原因完全无关。

**原因**：写 `def require_admin(request: Request)` 时直接把它当作参数默认值
（`user = require_admin`），FastAPI 会把它当成**普通参数**处理并调用它，
而不是走依赖注入。正确写法是 `user: dict = Depends(require_admin)`。

## 六、跑评估前的注意事项

**必须先停掉后端服务。**

评估脚本与后端服务会同时向同一个 Ollama 发请求，GPU 争用会改变模型输出分布，
导致同一配置测出不同结果（本项目实测出现过同一配置
`fp=9 / 19 / 20` 三种结果，且**看起来是可复现的**）。

正确做法：

1. 停后端（确认端口已释放）
2. 单进程跑评估
3. 需要对比两种配置时，用**交错顺序**（A→B→A→B），而不是先跑完 A 再跑 B
4. 保留一个"本应无差异"的对照组来探测环境噪声

详见 [`失败案例集.md`](失败案例集.md)。
