## 一、环境与部署类（9 例）

### 案例 1：模型仓库在国内下载速度受限

| 项        | 内容                                                                                 |
| -------- | ---------------------------------------------------------------------------------- |
| **现象**   | 从 ollama.com 下载 1.47GB 安装包，速度仅 **90KB/s**，预计剩余 **5 小时**；按此速度 6.7GB 模型需 20 小时以上     |
| **排查**   | 同期从 PyTorch 官方源下载 2.5GB 达到 **9.7MB/s** → 证明不是本地网络问题，而是该服务器在国内的链路受限                 |
| **根因**   | 官方分发服务器未在国内部署 CDN 节点                                                               |
| **解决**   | 安装包改用 GitHub 加速代理；模型改用**魔搭（ModelScope）**&#x4E0B;载 GGUF 后通过 Modelfile 导入 Ollama     |
| **论文结论** | 国内部署开源大模型时，**分发渠道的选择对开发效率的影响往往超过技术选型本身**；应准备多套镜像备选方案（官方源 / GitHub 代理 / 魔搭 / HF 镜像） |
### 案例 2：split GGUF 分片文件无法被 Ollama 导入

| 项        | 内容                                                                                                                            |
| -------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **现象**   | 导入 7B 模型时报错 `Error: invalid split GGUF: split GGUF "qwen2.5-7b-instruct-q4_k_m-00001-of-00002.gguf" has 1 shards, expected 2` |
| **排查**   | 两个分片均在目录中且大小正确（3.99GB + 673MB）；改用二进制拼接后报 `must use llama.cpp split filename pattern`                                          |
| **根因**   | ① Ollama v0.35.1 对 split GGUF 的分片查找存在缺陷；② 单纯二进制拼接只能合并数据，无法修改文件头中的 `split.count=2` 标记                                          |
| **解决**   | 放弃分片方案，改用**单文件 GGUF**（Qwen2.5-3B-Instruct Q4_K_M，2.1GB），问题消失                                                                  |
| **论文结论** | 本地推理框架对模型文件格式的支持存在**版本差异**，单文件 GGUF 的兼容性优于 split GGUF；工程实现中应优先选择容错性更高的格式                                                      |
### 案例 3：conda 服务条款导致环境创建失败

| 项        | 内容                                                                                                                                           |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**   | `conda create -n campus-rag python=3.11` 报 `CondaToSNonInteractiveError: Terms of Service have not been accepted for the following channels` |
| **二次失败** | 按官方提示执行 `conda tos accept --override-channels --channel ...` 报 `unrecognized arguments` —— **官网给的命令与当前 conda 版本不兼容**                         |
| **解决**   | 执行不含该参数的 `conda tos accept`                                                                                                                  |
| **论文结论** | 工具链的官方文档可能与实际版本存在滞后，遇到报错应以**本地实际提示**为准而非照抄文档                                                                                                 |
### 案例 4：PowerShell 多版本共存导致 conda 初始化失效

| 项        | 内容                                                                                                                                                                                                                                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**   | VS Code 终端中执行 `conda activate campus-rag` 后，提示符不变，`where.exe python` 仍指向 base 环境                                                                                                                                                                                          |
| **排查过程** | ① `where.exe python` 只有一行 `D:\Miniconda3\python.exe`（base）<br />② 执行 `conda init powershell` 后仍无效，提示 `no change` / `modified C:\Users\...\Documents\WindowsPowerShell\profile.ps1`<br />③ 但 VS Code 的 `$PROFILE` 指向 **`Documents\PowerShell\`**（PowerShell 7），两者是**不同目录** |
| **根因**   | `conda init powershell` 写入了 **Windows PowerShell 5.1** 的配置目录，而 VS Code 使用的是 **PowerShell 7**，配置文件互不读取                                                                                                                                                                     |
| **二次问题** | 即使写对目录，`profile.ps1` 也无法加载，报 `PSSecurityException: 禁止运行脚本` —— 执行策略默认为 Restricted                                                                                                                                                                                          |
| **解决**   | ① `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`；② 最终方案是将 **VS Code 默认终端改为 cmd**，并**用绝对路径调用解释器**（`D:\Miniconda3\envs\campus-rag\python.exe`）                                                                                                                       |
| **论文结论** | Windows 下多版本 Shell 共存会导致环境初始化静默失效；**开发环境应显式指定终端类型，并在自动化流程中使用绝对路径解释器**，避免依赖交互式激活                                                                                                                                                                                           |

> 📌 **后续复现（2026-10-04）**：本项目进行结构精简时，把 `data/app.db` 迁移至 `data/db/app.db`，
> 而 `.gitignore` 中仍写的是旧的精确文件名 `data/app.db*` —— **同类问题再次出现**。
> 这说明该缺陷的根源不是"忘了写"，而是**"忽略规则与文件位置存在隐式耦合"**：
> 一旦文件位置变动，忽略规则就静默失效（`git status` 不会报警）。
>
> **改进做法**：忽略规则应针对**目录**（`data/db/`）而非**精确文件名**，
> 并在移动文件后立即执行 `git status --ignored` 复核。
### 案例 5：pip 镜像源返回空索引

### 案例 6：`.gitignore` 缺失导致模型权重被提交

| 项        | 内容                                                                                       |
| -------- | ---------------------------------------------------------------------------------------- |
| **现象**   | 首次提交显示 `30 files changed, 103 insertions(+), 85902 deletions(-)`，其中 28 个是模型权重文件（含两份重复副本） |
| **根因**   | `.gitignore` **未在首次 `git add` 之前建立**                                                     |

### 案例 8：uvicorn worker 子进程残留，导致测试打到旧代码 ⚠️

| 项 | 内容 |
|---|---|
| **现象** | 修改了代码并重启服务后，**测试结果与改动不符** —— 明明改了 `sources` 置空逻辑，实测仍返回 5 条引用；同一份代码反复验证结论不一致 |
| **排查过程** | ① 先怀疑改动没生效 → 静态检查代码，确认改动已写入<br>② 再怀疑测试脚本问题 → 换写法重测，现象依旧<br>③ 执行 `netstat -ano \| findstr :8000 \| findstr LISTENING` → **发现一个"已停止"的 uvicorn 进程仍监听 8000 端口**<br>④ 新进程因端口被占**绑定失败**，请求实际仍由**运行旧代码的残留进程**处理 |
| **根因** | `python -m uvicorn ...` 在 Windows 上会 spawn 一个 **worker 子进程**；任务结束时用 `proc.terminate()/proc.kill()` **只杀掉父进程**，worker 残留并继续监听端口 |
| **解决** | ① `netstat -ano \| findstr :8000 \| findstr LISTENING` 取得 PID<br>② `taskkill /F /T /PID <PID>` —— **`/T` 必须加**，它负责终止整棵进程树<br>③ 启动前先确认端口空闲；停止时用同一条 taskkill |
| **验证** | 清理后重跑，所有断言与代码改动一致 |
| **论文结论** | Windows 下用进程管理器 API 终止多进程服务时，**只杀父进程会导致子进程残留**；验证服务类改动前应先确认"请求由哪个进程处理"，否则会得到自相矛盾的结论、浪费大量排查时间。此类"服务未真正重启"的问题在开发中具有普遍性 |
### 案例 9：`.gitignore` 只写主文件名，漏掉 SQLite WAL 附属文件

| 项 | 内容 |
|---|---|
| **现象** | 为提升并发能力给 SQLite 开启 WAL 模式后，`git add` 把 `data/app.db-shm`（32 KB）与 `data/app.db-wal`（177 KB）一并提交进版本库 |
| **根因** | `.gitignore` 中写的是精确文件名 `data/app.db`。SQLite 开启 WAL 后会**额外生成两个附属文件**（`-shm` 共享内存索引、`-wal` 预写日志），它们不匹配 `data/app.db` 这条规则。这与案例 6（`.gitignore` 缺失导致模型权重被提交）属同一类问题：**忽略规则没有覆盖"由主文件派生的、运行时会自动生成的文件"** |
| **解决** | 在忽略规则中补上 `data/app.db-shm` 与 `data/app.db-wal`；对已提交的附属文件执行 `git rm --cached` 从版本库移除（**保留磁盘文件**，不影响正在使用的数据库） |
| **验证** | `git check-ignore -v data/app.db data/app.db-shm data/app.db-wal` 三条规则均命中；`git status` 恢复干净 |
| **论文结论** | 版本库忽略规则应按**文件族**而非单个文件名来写（数据库主文件 + WAL/SHM 附属文件、模型权重目录、日志轮转文件等）。具备"运行时自动派生"特征的文件尤其容易被遗漏，且往往体积可观 |

## 二、代码缺陷类（9 例）

### 案例 10：中文全角标点被误转为半角

| 项        | 内容                                                                          |
| -------- | --------------------------------------------------------------------------- |
| **现象**   | 清洗后 `（一）内容` → `(一)内容`；`测试：内容` → `测试:内容`                                     |
| **影响**   | 中文法规文档中 `（一）（二）` 是标准写法，转换后既不符合规范，也可能影响中文分词与检索匹配                             |
| **根因**   | 为满足"统一全半角"的要求，实现时采用了**无差别转换**规则                                             |
| **解决**   | 明确"统一"的方向：应是**将中文文本中混入的半角英文标点转为全角**，而非反向；中文全角标点原样保留。同时补充特判：数字后的英文句点视为序号，不转换 |
| **论文结论** | 文本规范化需求需明确**转换方向与边界条件**；"统一全半角"这类模糊描述容易导致实现偏差                               |
### 案例 11：序号中的英文句点被误转为中文句号

| 项        | 内容                                                         |
| -------- | ---------------------------------------------------------- |
| **现象**   | `1.手机APP报名` → `1。手机APP报名`，涉及 3 个文件共 **182 处**              |
| **影响**   | 中文里序号为 `1.` 或 `1、`，从无 `1。` 写法；会影响检索时的文本匹配                  |
| **根因**   | 修正案例 10 后引入的转换规则过于宽泛，把**序号点号**也当成了句末句点                      |
| **解决**   | 增加特判：句点前为数字且后紧跟非空白字符时，判定为序号，不转换                            |
| **验证**   | 精确正则 `\d。\S` 检测，**182 处 → 0 处**                            |
| **论文结论** | 规则式文本清洗存在**误伤风险**，每次调整规则都应配合**针对性的回归检测**（本例的检测正则是 `\d。\S`） |
### 案例 12：文本块大量碎片化，未落入设计区间

| 项        | 内容                                                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **现象**   | 首次切分产出 84 个块，其中 **67.9% 的块小于 400 token**，平均仅 295 token，最短 44 token（如仅含"格或退学手续。"一句）                                               |
| **根因**   | 设计中要求的"相邻小块合并"这一阶段**未真正生效**，导致条款被切成大量碎片                                                                                          |
| **影响**   | ① 碎片块向量信息量低，占用 top-k 名额却无有效信息；② 22k 字产出 84 块，块数虚高；③ **会导致后续"三种切分策略对比实验"不公平** —— 不是策略差，而是参数没调对                                    |
| **解决**   | 增加自底向上合并阶段：同 heading_path 内相邻块合并至 400–600 token；无法内部合并的小块与前一块合并                                                                  |
| **验证**   | 总块数 **84 → 42**；400–600 区间占比 **22.6% → 69.0%**；<400 块 **67.9% → 7.1%**；平均 token **295 → 543**；**且 char 偏移还原率保持 100%**（合并未破坏引用定位） |
| **论文结论** | 切分策略的实现细节（合并逻辑）对块质量的影响**大于策略本身的选择**；实验前必须验证参数是否真正落入设计区间，否则对比实验失去意义                                                               |
### 案例 13：标题识别规则过宽，把正文引导句当成标题

| 项        | 内容                                                             |
| -------- | -------------------------------------------------------------- |
| **现象**   | 某个块的 `heading_path` 末级为 `第六条 成绩填报及试卷查阅：`（**末尾多了冒号**）           |
| **根因**   | 标题识别规则把"以冒号结尾的条款行"也判定为标题，但该行实际是正文引导句（后接"（一）（二）"列表）             |
| **影响**   | 污染 heading_path，使该块的主题标识错误                                     |
| **解决**   | 增加判断：以 `：` 或 `:` 结尾的行视为**正文**而非标题                              |
| **论文结论** | 基于规则的文档结构识别需要**处理边界情形**；"第X条"既可能是短标题，也可能是长正文的开头，需结合长度与行尾标点共同判断 |
### 案例 14：参数默认值导致安全机制静默失效 ⚠️

| 项        | 内容                                                                                                                                                              |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**   | `is_answerable(results, threshold=None, use_llm_check=True, question=None)` —— 调用方不传 `question` 时，**LLM 二次判定被静默跳过，直接返回 True**。实测调用耗时 **0.0s**（若真调用 LLM 应约 2.2s） |
| **影响**   | 契约设计缺陷：漏传一个可选参数即**无提示地关闭了拒答安全机制**，系统会对无依据的问题判定为"可回答"                                                                                                            |
| **解决**   | 将 `question` 改为**必填位置参数**；返回值由 `bool` 改为 dict，携带 `answerable` / `reason` / `stage` / `elapsed`，使判定路径**可观测**                                                     |
| **验证**   | 改造后判定耗时 2.14–2.16s，`stage` 字段正确区分 `threshold`（阈值拦截）与 `llm`（二次判定）                                                                                                |
| **论文结论** | **安全相关的开关不应有"静默关闭"的默认值**；关键判定路径应返回结构化信息（含 stage），以便评估阶段统计拦截来源                                                                                                   |
### 案例 15：不可回答时仍调用生成模型，产出无意义拼接

| 项        | 内容                                                                               |
| -------- | -------------------------------------------------------------------------------- |
| **现象**   | 问"校长办公室的电话是多少"，系统输出：<br />`[2] 校长办公室的电话是桂林电子科技大学校长办公室 2020 年 6 月 28 日印发`         |
| **危害**   | 该回答**没有任何电话号码**，却把参考资料中的日期、文号碎片拼成了貌似回答的句子。相比明确拒答，这种输出**更容易误导用户**                 |
| **根因**   | ① 案例 14 导致判定失效（判为可回答）；② 判定为不可回答时仍会调用生成模型，依赖模型"自觉"拒答                              |
| **解决**   | **两层防护**：① 判定不可回答时**直接返回预设拒答话术，不调用生成模型**（该分支生成耗时 0.00s）；② 在系统 Prompt 中明确禁止拼接无关片段 |
| **验证**   | 修复后 3 道无依据问题全部明确拒答，**未再出现碎片拼接**                                                  |
| **论文结论** | 拒答应在**管线层面强制拦截**，而非依赖生成模型的自觉；"判定不可回答 → 不生成"这一设计同时降低了延迟（生成耗时归零）与幻觉风险              |
### 案例 16：合并逻辑破坏字符偏移的风险（被验证规避）

| 项        | 内容                                                                    |
| -------- | --------------------------------------------------------------------- |
| **现象（风险，实际未发生）** | 案例 12 的修复需要合并文本块，而合并会改变 `char_start` / `char_end`，**一旦算错则全文引用定位全部失效** |
| **应对**   | 在修复要求中明确：合并后必须重新计算偏移，且**偏移还原率不得低于 95%**；修改后立即回归验证                     |
| **验证**   | 42/42 块偏移仍可 100% 还原（`原始文本[char_start:char_end]` 能正确切片出块内容）            |
| **论文结论** | 修复一个问题时须**明确另一个不可退化的指标**并做回归验证，否则易出现"修一处、坏一处"                         |

### 案例 17：FastAPI 依赖漏包 `Depends` 导致静默传入错误对象 ⚠️

| 项 | 内容 |
|---|---|
| **现象** | 实现"管理员权限"依赖 `require_admin` 后，本批**没有任何管理接口**，该依赖从未被调用。下一批接入语料导入接口时——只要真把它当依赖用——立刻报 `TypeError: 'function' object is not subscriptable`，即 `user["role"]` 里的 `user` 竟是个**函数对象** |
| **排查** | 用 `get_dependant()` 检查 FastAPI 解析出的依赖树，两种写法结果完全不同：<br>`def route(user: dict = require_admin)` → **子依赖数 0**（FastAPI 把它当成普通参数的默认值，直接零参调用）<br>`def route(user: dict = Depends(require_admin))` → **子依赖数 1**（正常注入） |
| **根因** | 项目里同时存在两种"依赖"形态，**名字对称但用法相反**，极易混淆：<br>① `require_user = Depends(get_current_user)` —— 本身是 **Depends 实例**，赋给默认值即可被识别，**不能再包一层**（包了会得到 `Depends(Depends(...))`）；<br>② `require_admin` 是**普通函数**，路由里必须写 `Depends(require_admin)`，**漏包就被当作普通参数默认值**。<br>更隐蔽的是：`get_current_user` 的形参是 `Request`，若在 `require_admin` 里写成 `Depends(get_current_user)` 再被当成普通参数零参调用，报错信息只会显示"函数不可下标"，与真实原因（漏包 Depends）看起来毫无关系 |
| **影响** | 属于**死代码里的缺陷** —— 依赖定义时不错、导入时不报错、全批测试全绿，**直到第一个真正的管理接口出现才暴露**。若管理接口晚做或未测，会一路潜伏 |
| **解决** | 把 `require_admin` 改写成**普通函数 + `Request` 形参**（内部自行调用 `get_current_user(request)`），只保留一种正确用法：`Depends(require_admin)`。这样漏包时 FastAPI 会**明确报参数错误**，而不会静默把函数当成用户对象 |
| **验证** | 用 `TestClient` 挂一个**临时管理接口**（不改动生产代码）真实触发该依赖：<br>不带 token → **401**；student token → **403 "需要管理员权限"**；admin token → **200**；非法 token / 缺 Bearer 前缀 → **401** |
| **论文结论** | ① 框架的依赖注入对**"默认值是不是依赖对象"高度敏感**，同名依赖若形态不统一（一个是 `Depends` 实例、一个是普通函数），必然误用；应对每个依赖**只保留一种调用写法**。<br>② **未被任何接口使用的鉴权代码等于未测试的代码**。权限这类安全相关逻辑，不应等到"第一个业务接口"才首次执行，而应通过临时接口或单元测试**提前触发**。<br>③ 本项目由此确立做法：**权限依赖写完后立即用最小接口实测 401/403/200 三条路径**，再进入业务开发 |

### 案例 18：文件扩展名与语言不匹配 —— 用 Python 的 docstring 写 `.js` ⚠️

| 项 | 内容 |
|---|---|
| **现象** | 把前端令牌存储从 `localStorage` 改为 `sessionStorage` 时，顺手给 `token.js` 加了一段**文件头说明**。前端构建立刻失败：<br>`Failed to parse source for import analysis because the content contains invalid JS syntax.` |
| **根因** | 写文件头时沿用了 Python 的习惯 —— **三引号 `"""..."""` 块注释**。JS 没有这种语法，`"""` 会被解析为字符串字面量拼接，直接语法错误。<br>根因不在改动的**逻辑**（三行 API 替换本身正确），而在**给 .js 文件写注释时套用了 .py 的写法** |
| **为何没被更早发现** | 改完 `token.js` 后**先做的是接口链路测试**（登出验证 7 项全通过），**与前端无关**。直到跑 `npm run build` 才暴露 —— 说明**后端测试通过不能代表前端可构建**，两端的验证必须都做 |
| **解决** | 把文件头改为 JS 的 `/** ... */`（JSDoc 风格）。同时检查了 `src/` 下全部 `.js` 文件，确认无其他三引号残留 |
| **验证** | ① `npm run build` 通过<br>② 从 Vite 的 dev 产物中**去掉注释后**统计真实调用：`sessionStorage` 3 次、`localStorage` 1 次（仅遗留清理）<br>③ 扫全项目 `.js` 文件确认三引号 0 处 |
| **论文结论** | ① 多语言项目里，**注释语法是最容易"串味"的地方** —— 逻辑代码有 IDE 提示，注释没有；<br>② **改完前端必须跑一次构建**，不能只看后端测试通过；构建是前端唯一能发现语法错误的关口（Vue 模板与 `<script setup>` 都在此时编译）；<br>③ 本案例与案例 4、9 同属「**格式/语法层面的低级错误，但只在特定环节才暴露**」这一类 |
| **案例价值** | 它是一处**"AI 辅助开发"特有的失误模式**：训练语料里 Python 代码占比高，给非 Python 文件写注释时会不自觉地沿用 Python 语法。防范办法是**每次改完立刻构建/编译**，而不是靠肉眼检查 |

### 案例 19：小模型复读 Prompt 示例导致判定误判 ⚠️

| 项        | 内容                                                                                                                                                |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**   | 问"学生可以申请休学吗"，LLM 原始输出为：<br />`问题"学生可以申请休学吗"，资料含"学生休学期间……"等条款 → YES`<br />但系统判定为 **False**（假阴性）                                                    |
| **排查**   | 解析代码为 `head = text.upper()[:40]; if "YES" in head ... elif "NO" in head`。LLM **复读了 Prompt 中的示例**，而示例含 `→ NO` 字样，落在前 40 字符内，被优先匹配                  |
| **根因**   | ① Prompt 把示例与输入混排，且示例中用 `→ NO` 这种易被复制的格式；② 解析只看前 40 字符，未考虑复读                                                                                      |
| **解决**   | **两端同时改**：① 重写 Prompt —— 示例改为「判定规则说明」的文字描述，去掉箭头，把问题与资料放在**最后**并明确"不要复述"；要求输出以 `结论：YES` / `结论：NO` 开头；② 解析改为优先正则匹配 `结论：YES/NO`，回退时取**最后出现**的 YES/NO |
| **验证**   | 构造 5 个样本测试解析鲁棒性 **5/5 通过**，其中包含关键样本 `（复读内容）... → NO ... 结论：YES` → 正确返回 True；6 题端到端 **6/6 正确**                                                     |
| **论文结论** | 小参数模型（3B）**复读 Prompt 内容的倾向明显**，使用 LLM 作为判定器时必须：① 把指令与数据分区；② 约定机器可解析的输出格式；③ 解析器需对复读具备鲁棒性                                                           |
### 案例 20：单一向量相似度阈值无法可靠判定"能否回答" ⚠️

| 项             | 内容                                                                                                                                                                |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**        | 用 top-1 向量相似度阈值判定可回答性时，**正确命中与错误命中的分数区间重叠**：<br />正确命中：0.5629 / 0.6045 / 0.6113 / 0.6423 / 0.6590 / 0.6827 / 0.7321<br />**错误命中：0.6048**（问"奖学金怎么申请"，命中"求职创业补贴手册"） |
| **影响**        | 该错误命中落在正确区间内部，**任何单一阈值都无法分离**，导致"知识库中无答案"的问题被误判为可回答                                                                                                               |
| **解决（当前）**    | 增加 **LLM 二次判定**：阈值初筛通过后再由 LLM 判断资料是否真正回答问题。实测可拦截该错误命中                                                                                                             |
| **解决（阶段三实测结论）** | 引入 **Cross-Encoder 重排**作为更可靠的判定依据 → **实测收益为负**（见案例 21、22）：检索指标显著提升（MRR +20.0%），但端到端拒答查准率反而下降（0.211 → 0.182）。**最终决定不启用重排**（`RERANK_ENABLED=False`）。<br>进一步实验证明：瓶颈在**判定环节**而非检索或排序（判定窗口扩到全覆盖仍不改善），详见 `eval/exp_e3_rerank.md` |                                                                                                             |
| **论文结论**      | 在中文短问题 × 长文本块的检索场景中，**密集向量相似度的绝对值不足以作为置信度指标**；拒答判定需要二次判别（重排或 LLM 判定），这一结论本身构成了本课题"引入重排与拒答机制"的实验依据                                                                 |
### 案例 21：判定器对措辞组合"稳定地判错"—— 过度拒答的真正根因 ⚠️

| 项 | 内容 |
|---|---|
| **现象** | 有些问题**答案明确存在于资料中，判定器仍返回"不能回答"**。例如：问「国家奖学金和国家励志奖学金能同时拿吗？」，资料为「同一学年内，获得国家奖学金的家庭经济困难学生可以同时申请并获得国家助学金，**但不能同时获得国家励志奖学金**或自治区人民政府奖学金。」—— 答案就在句中，判定器仍判 NO |
| **发现方式** | E3 重排消融实验中，重排后 4 道原本可答的题变成拒答。修复"分数口径不一致"（案例 22）后仍未恢复，于是把**含答案的文本块单独提交给判定器**，发现它照样判 NO |
| **排查过程** | ① 先怀疑随机性 → 同一输入重复 5 次，**输出完全一致**（0/4 题不稳定），排除随机性<br>② 再做健康检查：4 组"问题 + 明确含答案的资料"，**2 组判对、2 组判错**，且都稳定<br>③ 排除检索问题（含答案的块在 rank1）、排除截断问题（资料仅 40 字） |
| **根因** | 判定器（`qwen2.5-3b-q4`）的判定能力边界 —— 它**不是随机出错，而是稳定地在某些措辞组合上判错**。实测判错的两种情形：<br>· 资料为「……应在该课程成绩公布后**两周内**提出书面申请」→ 判 NO（问题是"有时间限制吗"）<br>· 资料为「……**不能同时获得**国家励志奖学金」→ 判 NO（问题含"能同时拿吗"）<br>两者的共同点：**问题与资料存在"否定/反问"式的对应关系**，模型可能被这种表层对立误导 |
| **影响** | 这是**过度拒答（15/61 = 26%）的真正根因**。之前几轮一直归因于"检索"或"排序"，本案例通过受控实验将其定位到**判定环节** |
| **修复尝试（2026-10-05）→ ❌ 失败，已回滚** | 按三个失败机制改写了判定 Prompt（否定式对应 / 隐含要素 / 条款片段无主语），<br>**判定层台架上测得「过度拒答 16→9」，看似成功**；<br>但在**停止后端服务、排除 GPU 竞争**后做交错 A/B 对照（旧→新→旧→新）：<br>`旧 Prompt: fp = [20, 20]`　`新 Prompt: fp = [20, 20]`　**逐题判定 0 处不同**<br>→ **该改动实际无效**，已回滚（Prompt 与 `max_check` 均恢复原值） |
| **★ 失败的原因：测量污染（本案例真正的价值）** | 评估脚本与后端服务**同时向同一个 Ollama/GPU 发请求**，输出分布被扰动。同一配置因此先后测出 **fp=9 / fp=19 / fp=20** 三种结果；更危险的是它**看起来可复现**（连测两次都是同一个值），极易误判。<br>停止后端后连测三次均为 **fp=20**，交错 A/B 四轮**全部一致**、逐题 0 处不同 —— 说明**系统本身是确定性的**，噪声全部来自并发争用 |
| **方法论修正（须写入论文）** | ① 本地 LLM 的判定类实验**必须在单进程、无服务占用的环境下**做；<br>② 必须**交错对照**（A→B→A→B），而非"先测 A 再测 B"，否则时间漂移会被误认为处理效应；<br>③ **单次测量的"可复现"（连测两次一致）不足以证明结论可靠** —— 本次污染的两次测量也确实一致；<br>④ 应保留一个**本应无差异的对照组**（本例中旧/新 Prompt 各跑两次）来探测环境噪声 |
| **论文结论（更新）** | 该过度拒答**无法通过改写判定 Prompt 消除**。结合"扩大判定窗口无效"的结论，可以确认：在本地 3B 模型的约束下，这一部分过度拒答是**判定环节的能力边界**，改进方向只能是把判定与生成换成更强的模型（与课题的本地部署前提冲突），或引入外部结构化判据。<br>**本案例更重要的产出是方法论层面的**：它揭示了"评估环境本身会成为实验变量"这一在单机 LLM 实验中容易被忽视的陷阱 |
| **论文表述建议** | > 定向实验表明，判定器在部分措辞组合下会稳定地给出错误判定：即使将包含明确答案的文本块单独提交，同一输入重复 5 次仍全部返回"不能回答"。这说明系统的拒答表现主要受限于判定环节而非检索环节 —— 检索侧 gold 块平均排名 1.86、top-3 覆盖率 49/56，已不构成瓶颈。 |
| **案例价值** | ① 它把"过度拒答的根因"从**推论**变成了**受控实验证明**（检索侧、排序侧、判定侧三层证据链）；<br>② 它示范了一种**归因方法**：当"检索+重排都无效"时，应把最小可判定单元（含答案的单块）单独喂给判定器，以此隔离变量；<br>③ 它说明**"模型稳定"不等于"模型正确"** —— 项目此前验证过判定器"输出稳定"（5/5 一致），当时以为稳定就等于可靠，本案例纠正了这一误解 |

### 案例 22：重排路径的分数口径不一致 —— "重排越正确，越容易被拒答" ⚠️

| 项 | 内容 |
|---|---|
| **现象** | 启用重排后，**原本能正常回答的问题变成了拒答**（4/61 题反向恶化）。典型：问「国家奖学金一年给多少钱？」，无重排时答出"每生每年10000元"，重排后拒答 |
| **排查** | 对比同题在两种配置下的 rank1 及其分数：<br>· 无重排：rank1 = `gjjxj_2026_0002`，`score = 0.6572` ≥ 0.62 → **早停放行** → ✅ 答出<br>· 重排后：rank1 = `gjjxj_2026_0001`，`score = 0.6150` < 0.62 → 落到 LLM 判定 → ❌ 拒答<br>而重排给出的 `rerank_score = 0.9546`（重排认为高度相关） |
| **根因** | `src/reranker.py` 把重排分数存入**独立字段** `rerank_score`，但 `score` 字段**仍是该块的稠密相似度**。而下游两道门限——阈值初筛（`SCORE_THRESHOLD=0.45`）与早停（`0.62`）——**都读 `score`**。<br>关键：**重排的作用恰恰是"纠正稠密的错误排序"**，因此被它提上来的块，其稠密分数往往天然偏低。实测 **dev 集 49%（30/61）的题目在重排后 rank1 稠密分数低于 0.62** |
| **后果** | 出现反常现象：**重排越正确地纠正排序，越容易把候选推进 LLM 判定**，而判定正是过拒的来源 |
| **解决** | ① `verify_answerable` 新增 `allow_early_stop` 参数（默认 `True`，不影响既有路径）<br>② `is_answerable` 新增 `use_rerank` 参数（默认取 `self.use_rerank`）；**重排路径跳过基于绝对分数的两道门限**，直接交给 LLM 逐块判定<br>③ 理由写进代码注释：这两个阈值都按稠密相似度标定，与重排后的排序**量纲不可比** |
| **验证** | · 重排路径日志出现「早停已禁用（重排后的 score 与阈值不可比）」<br>· 默认路径（`use_rerank=False`）行为完全不变，回归通过（拒答时 `generate` 仍为 0.0） |
| **修复效果** | 4 道反向恶化题中**仅 1 道恢复**，其余仍拒答 → 引出案例 21 的深入排查。**即：修好口径并未改善拒答，因为根因在判定器** |
| **论文结论** | ① 引入新的排序信号（重排分数）时，**必须同步审计所有消费旧信号的判据**，否则会出现"新信号提升了排序、旧阈值却把好结果拦下"的错配；<br>② 这是一个**接口一致性**问题而非算法问题 —— 值得作为"系统集成中的隐蔽缺陷"写进论文的实现章节 |
| **案例价值** | 它与案例 17（`Depends` 漏包）、案例 8（uvicorn 残留）同属"**接口/契约不一致导致的静默错误**"：不报错、测试能过、但行为反常。此类缺陷的共同特征是**症状与原因在代码上相隔很远** |

### 案例 23：一个问号决定答不答 —— 绝对阈值在分数密集区不可靠 ⚠️

| 项 | 内容 |
|---|---|
| **现象** | 同一个问题，只差一个全角问号，系统行为完全反转：<br>`考试不及格可以补考吗` → rank1=**0.6423** ≥ 0.62 → 触发早停 → ✅ 正常回答<br>`考试不及格可以补考吗？` → rank1=**0.6145** < 0.62 → 走逐块判定 → 3 块全 NO → ❌ 拒答 |
| **发现方式** | 端到端验收时，我（复核方）用带问号的问法复测此前验收通过的题目，意外触发拒答。**功能测试全部通过，只有改变输入的表层形式才暴露** |
| **排查过程** | ① 先怀疑是刚做的改动引入回归 → 逐步回退验证，确认与改动无关<br>② 对照两种问法 → 定位到唯一差异是问号<br>③ 扩展到实验验证：对 dev 集 61 题各跑两种问法（实验记录见 `eval/exp_punct_sensitivity.md`） |
| **根因（两层）** | **① 表层**：去首尾标点会让稠密检索的相似度得分系统性上升。61 题中 **60 题**的 rank1 上升，平均 **+0.019**<br>**② 本质**：该效应不是"检索变好"，而是**幅度不均的扰动** —— 同一题内不同候选的增幅极差平均 **0.0093**，而候选之间的分数差常仅 **0.005 量级**。于是 47/61 题的 top-10 排序被打乱，Recall@5 反而从 0.9123 降到 0.8860<br>**③ 判据层**：早停阈值 0.62 是**绝对相似度阈值**。在候选分数密集（分差 0.005）时，任何 0.009 量级的扰动都能翻转判定结果 —— **阈值附近的判定本质上是噪声驱动的** |
| **为什么不修** | 有两条看似可行的修法，**均不采用**：<br>**① 查询归一化（去标点）**：实测四项指标互相矛盾 —— rank1 上升 ✅、早停 +4 题 ✅，但 **Recall@5 −0.026 ❌、排序稳定性 47/61 题被扰动 ❌**。效应幅度（0.019）与候选分差（0.005）同量级，方向不可预测（哪题变好、哪题变坏无规律）。用召回与排序稳定性换早停收益，不划算<br>**② 下调早停阈值到 0.60**：如上，安全窗口只有 0.0019（见案例 20），属过拟合 |
| **处理方式** | 作为**已知局限**记录，并在论文中说明；改进方向（相对判据替代绝对阈值、引入 Cross-Encoder 重排）列入后续实验 |
| **论文表述建议** | > 实验表明，用户输入的表层形式（标点）会系统性影响稠密向量检索的相似度得分：去掉首尾标点后，61 道测试题中 60 题的 top-1 相似度平均上升 0.019。然而该效应并非检索能力的提升 —— 同一批候选上的分数增幅不均（题内极差约 0.009），导致 47/61 题的 top-10 排序发生改变，Recall@5 反而下降 0.026。这说明**在候选分数密集（分差约 0.005）时，检索排序对微小扰动高度敏感**，基于绝对相似度阈值的判定缺乏鲁棒性。 |
| **案例价值** | ① 它是**第三个支持引入重排的实证**（前两个：案例 20 的阈值不可分离、国家奖学金问题的答案块排名靠后）；<br>② 它揭示了一个**方法论问题**：绝对分数阈值在候选分数密集时不可靠，应改用相对判据；<br>③ 它示范了"功能测试通过 ≠ 系统鲁棒" —— 只有**系统地变化输入形式**才能暴露此类问题 |

## 五、设计边界类（1 例）

### 案例 24：密集课程表导致"单门课程字段查询"失效 ⚠️

| 项 | 内容 |
|---|---|
| **现象** | 问"大学体育这门课多少学分"，系统判定为**不可回答**并拒答。而正确答案就在 rank1 的块里 |
| **实测数据** | 检索结果 `pyfa_ruanjian_2025_0030`，分数 **0.6057**，880 字符 / 544 token；该块内容形如 `课程代码： 000005；课程名称： 大学体育2；…；学分： 1；总学时： 36；…`，**这一块里塞了 9 门课程的完整字段** |
| **根因（两层）** | **① 检索层**：rank1 分数 0.6057 略低于早停阈值 0.62，未触发早停，走了逐块判定路径<br>**② 判定层**：逐块判定把整块（9 门课）送入 LLM，模型需从 9 门课程的密集字段中定位"大学体育"这一门，判为 NO |
| **更深层原因** | **块的粒度与查询的粒度不匹配** —— 块是"多门课程打包"，查询是"单门课程的单一字段"。这与开题报告中"课程表等强结构化表格信息不作为检索问答对象"的设计边界直接相关 |
| **为什么不修** | 两条看似可行的修法**都不应采用**：<br>**① 早停阈值 0.62 → 0.60**：本例 rank1=0.6057，降阈值即可命中。但本轮拒答题最高分仅 0.4764，**降阈值在测试集上不显示任何副作用**，却会在真实场景放行更多"低分但命中"的假阳性。更关键的是，已经完成的判定策略对照实验（方案C 拒答侧仅 2/4）**恰好证明了低阈值的危害**，为单一题目回头降阈值等于推翻自己刚得出的结论<br>**② 按课程实体拆分文本块**：需改动 `chunker.py` 的切分算法，牵动已验收的全部指标（块长分布、碎片率、偏移还原率），风险远大于收益 |
| **处理方式** | 作为**已知局限**记录并在论文中说明；改进方向（按课程实体拆分块、建立表格结构化索引）列入后续工作 |
| **论文表述建议** | > 系统对"某门具体课程的学分/学时"这类**课程表字段级查询**支持有限。实测表明，当课程表被组织为包含 9–10 门课程的密集文本块时，检索排序与逐块判定均难以准确定位到单一课程。本课题已将此类查询声明为研究范围之外；其改进方向（按课程实体拆分文本块、建立表格结构化索引）留待后续工作。 |
| **案例价值** | 这是开题报告中"表格不作为问答对象"这一局限声明的**真实实证** —— 不是"我们没做好"，而是"我们预先界定了边界，并在此验证了边界的真实存在" |

**附：逐块判定引入的取舍（可写入论文分析）**

| 查询类型 | 拼接判定（旧） | 逐块判定（新） |
|---|---|---|
| 规章/通知类的条件与流程问答 | ❌ 误拒 3 题 | ✅ 全部修复 |
| 拒答侧正确性 | 4/4 | **4/4（保持）** |
| **课程表字段级查询** | ✅ 偶然可答（整表一次性送入） | ❌ 误拒（密集块超出判定能力） |

> **任何判定策略都有其适用的查询粒度**：逐块判定擅长"规章条款"这类**块级语义匹配**，但对"密集块中包含单一目标"的查询反而更弱。这一取舍本身即是分析素材。

### 6.2 三条最值得强调的经验

1. **实验前的参数校验不可省略**（案例 10）  
   切分策略的实现细节对块质量的影响大于策略本身；若参数未落入设计区间，三种策略的对比实验将失去意义。本课题通过"块长分布 + 偏移可还原率"两项指标做前置校验。
2. **拒答必须在管线层面强制实现**（案例 12、13）  
   依赖生成模型"自觉拒答"不可靠：既可能输出无意义拼接，也无法保证延迟。本课题的做法是"判定不可回答 → 直接返回预设话术，不进入生成阶段"。
3. **用 LLM 做判定器时必须考虑输出鲁棒性**（案例 15）  
   小参数模型会复读 Prompt；正确做法是"指令与数据分区 + 约定可解析格式 + 解析器容错"，三者缺一不可。
4. **"模型输出稳定"不等于"模型判定正确"**（案例 20）  
   本课题曾验证判定器"同一输入重复 5 次输出一致"，当时据此外推为"判定可靠"。后续定向实验推翻了这一推论：对另一批输入，它同样稳定地给出**错误**判定（答案明确在资料中，5/5 全判 NO）。  
   **教训**：稳定性（determinism）与正确性（correctness）是两个独立维度。用小模型做判定时，除稳定性测试外，**必须构造"答案明确存在"的正例集做正确性测试**，二者不可互相替代。
5. **引入新信号时必须审计所有消费旧信号的判据**（案例 21）  
   重排引入了新的排序信号，但下游阈值初筛与早停仍读旧的稠密相似度字段，导致"重排越正确、越容易掉进 LLM 判定"。此类**接口/契约不一致**的缺陷不报错、测试能过，症状与原因在代码上相隔很远（另见案例 8、17、18）。
